The problem

Creators need product listings, imports, checkout and a buyer library. The difficult boundary is payment completion: a browser redirect is not proof that money settled. A buyer may close the tab, a gateway may retry a callback and two workers may confirm the same order concurrently. The marketplace needs one durable state change across all three entry points.

My contribution

I built Gumora as a full-stack creator marketplace with a decoupled Next.js client and Express API, MongoDB persistence, session authentication, Cashfree checkout and AI-assisted imports. The current public branch also contains subsequent review-driven reliability and security improvements. The source links below identify that current implementation rather than treating every hardening change as an original competition or commercial achievement.

The important invariant

The pending-to-paid transition and product sold-count increment happen in the same MongoDB transaction. The conditional pending-state update means a duplicate confirmation observes an already-settled order. A crash cannot commit the order without the sales update. The service checks for transaction support and refuses settlement on a standalone MongoDB server instead of falling back to two unsafe writes.

One authority, several triggers

Buyer confirmation, signature-verified webhooks and a reconciliation sweep call the same settlement service. The gateway payload identifies an order, while the backend fetches authoritative status from Cashfree and checks provider order ID, PAID status, currency and the exact minor-unit amount. This handles the buyer who never returns without trusting client-side success flags.

Security at adjacent boundaries

The API sets HttpOnly, Secure session cookies, but the reviewed default branch still has an authenticated /token route that returns the JWT and a refresh route accepting a token in the request body. A cookie-only session-security claim would therefore be inaccurate. This is an unresolved boundary in the published source, not a fix claimed by this case study. Separately, image imports use a public-address-only fetcher, revalidate redirects and cap streamed downloads before image inspection.

How it is checked

Settlement integration tests use a real MongoDB replica set and exercise concurrent confirmations, rollback and duplicate settlement. Separate standalone-server tests cover refusal when transactions are unavailable. Playwright tests isolate external services with mocks, so they check the application flow without charging a payment method. These linked tests are repository evidence; no real payment was performed for this portfolio.

Deployment and remaining limits

On 29 October 2026, the storefront returned HTTP 200, but the API health endpoint returned HTTP 503 with Render's Service Suspended page. Sign-in, catalog, checkout and library therefore cannot be presented as a working live demo. Local evaluation requires configured services and transaction-capable MongoDB. Signature verification, database correctness and a mocked browser test do not establish successful live payment processing.
