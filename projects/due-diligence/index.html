The problem

A property assessment combines heterogeneous records, risk scoring, generated explanations and downloadable reports. The engineering challenge is to make those parts cooperate while respecting ownership: an attractive report export must never bypass the authorization applied to the underlying report.

My contribution and shared ownership

The account-owned project README identifies me as Team 03 lead and attributes backend architecture, Spring Security/JWT authentication, service aggregation, six-category scoring and deployment orchestration to me. These are repository-documented contributions, not an independently verified employment certificate. The complete application is collaborative. Team membership counts conflict across older materials, so this page does not give a precise team size.

Architecture and data flow

A Next.js frontend calls Spring Boot controllers and services backed by PostgreSQL. The aggregation layer assembles property context; a weighted risk engine evaluates six categories; AI-assisted explanation and report generation consume that context. Controller, service and repository boundaries keep persistence separate from scoring and delivery. Generated conclusions depend on the completeness and quality of upstream data.

Authorization must survive export

Report PDF and Excel endpoints check ownership or administrator access rather than treating a report ID as permission. Property snapshot exports resolve the caller's latest report. The useful evidence is in the controller tests: another user's report, missing resources and allowed ownership paths need distinct behavior. AI text cannot replace these server-side checks.

A concurrency problem behind a small feature

Notification preferences may be created for the first time while report completion and the email listener race. PostgreSQL concurrency tests use latches and Testcontainers to reproduce that boundary. The documented checks cover one in-app notification and one email after commit, rollback behavior and SMTP failures. These later review fixes belong to the shared current codebase, rather than a claim that I personally authored every patch.

How it is checked

The repository contains JUnit service/controller tests, an H2 end-to-end workflow, PostgreSQL Testcontainers concurrency tests and frontend tests. Docker-dependent integration checks can be skipped when Docker is absent, so a generic green unit-test badge is insufficient evidence that the race ran. This portfolio links the relevant test files and does not claim to have rerun the application suite.

Deployment and limitations
