The problem

A purchase can fit today's balance and still make next month's rent unaffordable. This offline competition engine reconstructs cash states, forecasts commitments and compares payment plans against a minimum-balance constraint. The interesting problem is temporal: affordability must hold across the modeled forecast, rather than at a single instant.

My contribution

I developed the individual Buy or Wait? submission: the cash-state ledger, deterministic planning pipeline and reproducible output artifacts. The linked repository records the implementation, competition artifacts and subsequent review fixes. Its current test documentation is broader than the original competition result; these are different kinds of evidence.

Where financial authority lives

Messages and receipt extractions pass through a closed typed evidence schema before reaching the ledger. An optional model can extract facts, but cannot directly set a balance, change an exchange rate or rank payment plans. Missing debit amounts trigger a conservative failure rather than silently becoming zero. Pending debits are reserved; pending credits and unrealized investments do not become spendable cash.

The key algorithm

The forecast computes daily balances using Python Decimal. A suffix minimum answers how much can be paid on a day while preserving the minimum balance on every later modeled day. Full-payment, wait, two-payment and supplied installment candidates then pass a hard completion-deadline gate. Remaining plans are ranked by spending changes, total cost, start date and payment count. This makes the recommendation explainable through an actual bottleneck day.

Architecture and tradeoff

The pipeline moves from extraction to validation, ledger reconstruction, forecast, plan search and machine-readable proof. Outputs use sibling temporary files and atomic replacement; code fingerprints bind a recorded run to its implementation. The final submitted run reports zero live model calls, using offline rules and cached image extractions. That makes this run reproducible without a model provider, but does not establish general receipt-understanding capability.

How it is checked

The repository records 847 passing unit tests and four strict expected failures, plus 15 adversarial cases. These are historical repository results, not a new execution of that suite for this portfolio. The linked verification summary describes the commands, five output-validator warnings and the sample disagreements. Official result captures show rank #85 of 3,062 and score 68.2/100; the live contest portal may require authentication.

Failure modes and limits

The balance invariant applies to recognized events inside a finite calendar horizon. The recurrence estimator can miss irregular spending. Four sample divergences remain documented, including conservative spending estimates and different safe-payment dates. A competition score measures performance on that challenge; this is not a live banking integration or financial-advice service.
