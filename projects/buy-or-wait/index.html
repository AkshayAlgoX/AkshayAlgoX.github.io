Buy or Wait?

A Python engine that decides whether a purchase should be paid now, split into payments, or postponed.

View the code ↗

The problem

The challenge gave each person a stream of messages, receipts and bank events, and asked a simple-sounding question about a purchase: buy now, pay in parts, or wait?

The hard part is time. A purchase can fit comfortably in today’s balance and still push the account below its minimum two weeks later, when rent and a subscription renewal land on the same day.

How it works

The pipeline extracts facts from the messages, validates them against a closed schema, reconstructs a ledger in Python Decimal, projects every future day’s balance, and then searches payment plans.

Extraction can only produce typed facts. It can’t set a balance or choose a plan. A missing debit amount stops the case instead of silently becoming zero, and pending credits never count as spendable money.

The key idea: a suffix minimum

To pay an amount on day D, the balance must stay above the minimum on D and on every later day. So for each candidate day I compute the minimum projected balance from that day to the end of the forecast. The earliest day where that minimum covers the payment is the earliest safe day.

Full payment, waiting, two-part payment and any offered instalment plan are all checked this way. Plans that can’t finish before the deadline are dropped, and the rest are ranked by spending changes, total cost, start date and number of payments.

Built to be re-run

Outputs are written to temporary files and atomically renamed, and each recorded run is fingerprinted against the code that produced it. The final submitted run made no live model calls; image receipts used cached extractions, so the result can be reproduced without an API key.

Results

Final standing: individual rank #85 of 3,062, score 68.2 / 100. The repository now runs 846 tests (plus 1 skipped and 4 documented expected failures) from a clean clone; those tests were added and extended after the contest, so they describe the code today rather than the competition result.

What I’d do next

The recurring-spend estimator is deliberately simple and misses irregular spending, and four sample cases still differ from the published answers, mostly where my plan is more cautious about the safe payment date. I’d like a proper probabilistic forecast for irregular spending before trusting it with real money.
