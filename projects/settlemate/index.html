The problem

Financial reconciliation must distinguish a clean match from an uncertain explanation. An invoice may be paid in a split or grouped settlement; an AI-generated plausible story cannot make an incorrect total correct. SettleMate places matching and validation in deterministic code, then uses AI for advisory exception investigation.

My contribution

I developed the SettleMate reconciliation application and its separation between deterministic financial decisions and AI-assisted investigation. The current repository contains later solver-reference checks and signing-key hardening. The case study points directly to these implementations and records their boundaries rather than using a generic claim of autonomous financial correctness.

The active matching engine

Despite the historical CP-SAT class name, the application calls an exact TypeScript branch-and-bound search, not the separate Python OR-Tools service. It minimizes amount difference times 1,000 plus invoice count, subject to tolerance and cardinality constraints. Amounts are validated integer minor units. Search order is fixed by amount and ID, but a wall-clock timeout can vary with machine speed.

Bounded computation changes the claim

The policy searches at most 50 eligible candidates and normally at most eight invoices per split. Dropping candidates downgrades a found result to FEASIBLE, because it cannot establish optimality over the original request. The synchronous search can block the Node.js event loop up to its time ceiling. A feasibility verifier checks identifiers, tenant boundaries, totals and policy constraints; it does not independently prove optimality.

Receipts and proof artifacts

Canonicalized decisions are hashed and authenticated with HMAC-SHA256. HMAC verification requires the appropriate secret key material; these are not public-key signatures that any visitor can independently verify. Key versions and rotation govern which receipts can be trusted. Separately, integer invariant checks emit SMT-LIB scripts. External Z3 runs cross-check those concrete scripts; Z3 is not always executing inside the application and the artifact is not a theorem over every possible input.

How it is checked

The repository records 3,000 seeded cases compared with exhaustive subset enumeration and an OR-Tools model of the same policy. The test also corrupts totals, IDs and objectives to check verifier rejection. A separate recorded 2,000-case external Z3 comparison checks agreement between integer evaluation and exported scripts. These are bounded reference comparisons reported in the repository, not independent certification or tests rerun during this portfolio build.

Deployment and remaining limits

The Render URL returned HTTP 503 with Service Suspended on 29 October 2026. The case study therefore links source and local setup instead of advertising a working demo. Old accuracy, memory and throughput headlines are omitted here: meaningful performance comparisons need a named dataset, workload, environment and method. Timeout-dependent replay and candidate truncation remain explicit limitations.
