Financial reconciliation · Razorpay Track 04 challenge

SettleMate AI

A reconciliation tool that matches payments to invoices and uses an LLM only to investigate the exceptions.

View the code

Runs locally · hosted demo offline

The problem

Reconciliation looks simple until a customer pays three invoices with one transfer, a gateway deducts a fee, or two settlements land on the same day. Then the question becomes which combination of invoices this payment covers, and the answer has to be right to the paisa.

I didn’t want a language model deciding that. It can write a plausible story for a wrong total.

Design: deterministic decisions, AI for explanations

Every input is normalised to integer minor units first. Clean matches go through fast exact lookups. Split payments go to a combinatorial search, and only the cases that remain unresolved reach the AI investigator, whose output is advisory and checked before anything is recorded.

Where the LLM fits

When a case doesn’t resolve cleanly, an LLM investigator (OpenAI, Anthropic or Gemini, whichever key is configured) is asked for structured, checkable claims rather than prose: which record, which amount, which policy. A rule-based validator then checks each claim: evidence ids must exist and belong to the case, amounts must equal the source records to the paisa, and timing and policy claims are recomputed. A critic pass challenges anything left unverified.

Record text such as bank narrations is treated as data, never as instructions, and without an API key the system falls back to rule-based claims. The model’s output is advisory; it can’t write to the ledger.

The matching search

For a payment, the engine looks for the subset of eligible invoices whose total is closest to the payment, within a tolerance and a limit on how many invoices one payment may cover. The objective is the difference times 1,000 plus the number of invoices, so a smaller difference always wins and ties go to the simpler explanation.

It’s an exact branch-and-bound search in TypeScript. Invoices are sorted by amount, and any branch that already exceeds the payment is pruned. To keep requests bounded it looks at no more than the 50 smallest candidates, and it reports a result as merely “feasible” when larger candidates had to be skipped.

Checking the checker

A separate verifier re-computes every selection: ids, tenant, totals, tolerance and the objective. In tests the engine agrees with a brute-force enumeration of every subset on 3,000 seeded random cases, and with an OR-Tools CP-SAT model of the same rules. The verifier also rejects deliberately corrupted results. OR-Tools is used only as a cross-check; the app itself runs the TypeScript search.

Receipts

Each final decision is canonicalised, hashed and sealed with an HMAC receipt under a versioned server key, so a stored decision can be replayed and checked later. Because HMAC uses a shared secret, receipts are verified by the server, not by outside parties.

What I’d improve

The search runs synchronously on the Node.js event loop for up to its time limit, which is fine for a single user but should move to a worker for real traffic. The hosted demo on Render is currently offline; the repository has the full local setup.
